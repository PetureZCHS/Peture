# Supabase 后端敏感内容审查实施指导文档（后端工程师）

## 1. 文档目标

在当前 Supabase 架构上落地“可追溯、不可绕过、可扩展”的敏感内容审查体系，覆盖：

- 用户/宠物昵称与头像
- AI 助手输入与输出
- 成长日记输入与输出
- AI 生图实验室（原图与生成图）

并满足《实施参考建议》中“Edge Functions + 日志表 + 触发器 + Bucket 隔离 + RLS”的落地要求。

  - `moderation_logs`、`moderation_errors` 表
  - 审查触发器函数与触发器
  - 头像/生图临时桶与正式桶策略
  - 独立 `moderate-text`、`moderate-image` 函数

### 2.3 风险结论

- 审查逻辑尚未形成“后端强制闭环”，客户端绕过后可直接写库/写存储。
- 缺少统一审查日志，无法满足合规留痕和故障追踪。

## 3. 目标后端架构

### 3.1 核心组件

- Edge Functions
  - `moderate-text`：文本审查统一入口
  - `moderate-image`：图像审查统一入口
  - `chat` / `diary-v3` / `img-gen-start` / `img-gen-check-v2` 内嵌二次审查
- Database
  - `moderation_logs`
  - `moderation_errors`
  - 触发器（昵称、日记等）
- Storage
  - `avatars-temp` / `avatars`
  - `ai-images-temp` / `ai-images`
  - RLS + 生命周期清理策略

### 3.2 审查处理原则

- **fail-close**：高风险场景（头像、生图、公开文本）审查异常默认拒绝。
- **统一判定**：第三方返回结果在后端归一，前端不直接解读第三方原始结构。
- **日志先行**：每次审查无论通过/失败，优先落 `moderation_logs`。

## 4. 详细实施步骤

### 4.1 新增 Edge Function：`moderate-text`

### 输入

- `content: string`
- `scene: nickname | owner_nickname | pet_name | ai_input | ai_output | diary_input | diary_output`

### 输出（统一结构）

```json
{
  "passed": false,
  "scene": "nickname",
  "riskLevel": "high",
  "riskLabels": ["political"],
  "action": "block",
  "message": "内容包含敏感信息",
  "traceId": "uuid"
}
```

### 实现要点

- 从 `Authorization` 提取 JWT，使用 `supabase.auth.getUser` 获取真实 `user_id`。
- 调第三方文本审查（网易易盾或阿里云），将结果映射到统一结构。
- 截断 `content`（建议 500 字）写日志，避免日志表膨胀。
- 异常写 `moderation_errors`，并返回 500 + `traceId`。

### 4.2 新增 Edge Function：`moderate-image`

### 输入（二选一）

- `image_base64`（小文件）
- `storage_path`（推荐，前置上传临时桶）

### 输出

与 `moderate-text` 相同结构，`scene` 为 `avatar` / `pet_avatar` / `image_input` / `image_output`。

### 图像实现要点

- 对临时桶路径进行 owner 校验（防越权审查他人文件）。
- 审查通过后可返回 `suggested_action = move_to_formal_bucket`。

### 4.3 改造现有函数（强制二次审查）

#### 4.3.1 `chat/index.ts`

- 用户输入入模前调用文本审查（`ai_input`）。
- 流式输出完成后可选执行二次审查（`ai_output`）：
  - 同步阻断：返回替代安全文本
  - 或异步回写撤回标记（根据业务要求）

#### 4.3.2 `diary/diary-v3.ts`

- `inputs.query` 先做 `diary_input` 审查。
- 最终输出文本做 `diary_output` 审查，未通过则不返回原文，返回安全提示与风险码。

#### 4.3.3 `img-gen-start/index.ts` + `img-gen-check-v2/index.ts`

- `img-gen-start`：先校验原图 `image_input`，通过后才向上游申请任务。
- `img-gen-check-v2`：下载结果图后先做 `image_output` 审查，未通过不写正式桶。

## 5. 数据库与存储改造

### 5.1 新增迁移文件建议

- `supabase/migrations/20260402_create_moderation_logs.sql`
- `supabase/migrations/20260402_create_moderation_errors.sql`
- `supabase/migrations/20260402_add_moderation_triggers.sql`
- `supabase/migrations/20260402_storage_policies_for_moderation.sql`

### 5.2 `moderation_logs` 建议字段

- `id uuid pk`
- `user_id uuid`
- `scene text`
- `content_excerpt text`
- `resource_path text`
- `result text`（pass/block/review）
- `risk_level text`
- `risk_labels text[]`
- `provider text`
- `provider_response jsonb`
- `trace_id uuid`
- `created_at timestamptz default now()`

索引建议：

- `(user_id, created_at desc)`
- `(scene, created_at desc)`
- `(created_at desc)`

### 5.3 `moderation_errors` 建议字段

- `id uuid pk`
- `trace_id uuid`
- `user_id uuid`
- `scene text`
- `error_message text`
- `stack text`
- `created_at timestamptz`

### 5.4 触发器策略

优先对“不可绕过核心字段”建触发器：

- `users_profiles.nickname`
- `users_profiles.owner_nickname`
- `pets.name`
- `pets.owner_nickname`
- `pet_diaries.content`（若允许直写发布）

触发策略：

- `BEFORE INSERT/UPDATE` 调审查函数，不通过直接 `RAISE EXCEPTION`。
- 注意避免触发器递归与性能问题（仅在字段变更时触发）。

### 5.5 Storage Bucket 与 RLS

- 新建：
  - `avatars-temp`（私有，24h 清理）
  - `avatars`（正式）
  - `ai-images-temp`（私有，24h 清理）
  - `ai-images`（正式）
- RLS 原则：
  - `temp` 桶仅 owner 可读写
  - `formal` 桶按业务策略公开或仅 owner 可读
  - 禁止 `anon` 读取 `temp` 桶

- 文本场景：通过、拦截、超时、第三方异常、鉴权失败
