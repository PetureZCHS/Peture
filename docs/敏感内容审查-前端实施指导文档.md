# Flutter 客户端敏感内容审查实施指导文档（前端工程师）

## 1. 文档目标

基于仓库当前实现与《Flutter + Supabase App 敏感内容审查技术实现方案报告》中“实施参考建议”，将前端改造为“所有用户可编辑内容提交前必过审查”的统一机制，覆盖以下范围：

- 用户头像 / 昵称
- 宠物头像 / 昵称
- AI 助手（输入与输出）
- 成长日记
- AI 生图实验室

目标是：**前端不绕过、交互可解释、失败可回退、日志可追溯**。

---

## 2. 当前仓库现状与改造切入点

### 2.1 现有关键页面（必须接入审查）

- 用户昵称/头像
  - `lib/features/profile/presentation/profile_screen.dart`
  - `lib/features/profile/presentation/account_settings_page.dart`
- 宠物昵称/头像
  - `lib/features/profile/presentation/pet_profile_form_page.dart`
  - `lib/features/profile/presentation/profile_screen.dart`（新增/编辑宠物）
- AI 助手
  - `lib/features/chat/presentation/chat_page.dart`
  - `lib/services/supabase_edge_service.dart`（聊天 Edge 调用）
- 成长日记
  - `lib/features/diary/presentation/pet_diary_compose_page.dart`
  - `lib/services/supabase_edge_service.dart`（日记 Edge 调用）
- AI 生图实验室
  - `lib/features/image_generation/presentation/preparation_page.dart`
  - `supabase/functions/img-gen-start/index.ts`、`img-gen-check-v2/index.ts`（后端联动）

### 2.2 现状风险（前端视角）

- 目前没有统一“审查 SDK/网关”层，页面直接写业务提交，容易漏接。
- 多处昵称修改只做“非空+长度”校验，未做敏感审查。
- 头像链路存在本地文件和云端文件混用，缺少“临时桶 -> 过审 -> 正式桶”流程。
- AI 助手目前发送逻辑中存在“构造了 `queryToSend` 但实际调用仍传 `messageText`”的实现偏差，需同时纳入修正和审查接入。
- 生图当前主要是“图片+风格”，未显式用户 Prompt 输入，但仍需对上传图和生成图做图像审查。

## 3. 前端总体改造方案

### 3.1 原则

- **统一入口**：所有可编辑内容提交前，统一走 `ModerationClient`。
- **先审后写**：审查通过后才调用业务写接口（DB/Storage/Edge Function）。
- **场景化提示**：按 `scene` 返回不同提示文案，避免“审核失败”黑盒体验。
- **可降级**：审查服务异常时，不直接放行高风险场景（头像、生图、公开文本）。

### 3.2 建议新增目录

- `lib/features/moderation/domain/moderation_scene.dart`
- `lib/features/moderation/domain/moderation_result.dart`
- `lib/features/moderation/data/moderation_client.dart`
- `lib/features/moderation/presentation/moderation_dialog.dart`
- `lib/features/moderation/utils/moderation_error_mapper.dart`

### 3.3 与后端约定的最小响应结构

前端按如下最小字段解析（后端文档会给完整定义）：

```json
{
  "passed": true,
  "scene": "nickname",
  "riskLevel": "none",
  "riskLabels": [],
  "action": "allow",
  "message": "ok",
  "traceId": "uuid"
}
```

## 4. 分场景详细实施要求

### 4.1 用户昵称（`nickname`）

#### 4.1 接入点

- `profile_screen.dart` 的 `_showEditNicknameDialog`
- `account_settings_page.dart` 的 `_changeName`
- `account_settings_page.dart` 的 `_changeOwnerNickname`

#### 4.1 实施要求

- 在调用 `upsertUserProfile` 前，先调 `moderate-text`：
  - `scene = "nickname"`（主人称呼可用 `owner_nickname`）
  - `content = 用户输入`
- `passed=true`：继续写库；`passed=false`：阻断并展示风险标签（如涉政/色情/暴恐）。
- 将重复逻辑抽为 `Future<bool> guardNicknameAndSubmit(...)`，避免三处分叉。

#### 4.1 UI 要求

- 阻断弹窗标题统一：“内容不符合社区规范”
- 文案包含“可修改后重试”，不展示第三方服务商信息。

### 4.2 用户头像/宠物头像（`avatar`/`pet_avatar`）

#### 4.2 接入点

- `account_settings_page.dart` `_changeAvatar`
- `profile_screen.dart` `_changeAvatar`
- `pet_profile_form_page.dart` `_pickAvatar` + 保存流程

#### 4.2 实施要求

- 图片选择后先做本地压缩，再调用 `moderate-image`（base64 或上传 `temp_path`）。
- 通过后才允许上传正式存储并写 `avatar_url`/`avatar` 字段。
- 不通过则删除临时文件并提示违规原因类型（不回显原图）。
- 宠物头像与用户头像走同一套 `guardImageAndUpload(...)` 封装。

### 4.3 宠物昵称（`pet_name`）

#### 4.3 接入点

- `pet_profile_form_page.dart` 中 `_showNameInput` 和 `_savePetProfile`
- `profile_screen.dart` 宠物新增/编辑提交前

#### 4.3 实施要求

- 仅在 `_savePetProfile` 最终提交点做一次服务端审查（防重复调用）。
- 审查通过再 `insertPet` / `updatePet`。

### 4.4 AI 助手（输入 + 输出）

#### 4.4 接入点

- `chat_page.dart` `_sendMessage`
- `chat_page.dart` 流式输出处理 `ContentEvent` / `DoneEvent`

#### 4.4 实施要求

- 输入审查：
  - 用户消息发送前调用 `moderate-text`，`scene = "ai_input"`。
  - 不通过则不发起 `callDifyChat`。
- 输出审查：
  - 对流式内容做“完整消息结束后二次审查”（`scene = "ai_output"`）。
  - 若二次审查不通过：替换为安全提示文本，并记录消息撤回状态。

#### 4.4 必改缺陷（顺便修复）

- 当前 `_sendMessage` 构造了 `queryToSend` 但调用仍是 `query: messageText`。
- 调整为真实传递组装后的变量，再叠加输入审查结果，避免上下文丢失。

### 4.5 成长日记（`diary_input` / `diary_output`）

#### 4.5 接入点

- `pet_diary_compose_page.dart` `_generatePetDiary`
- 日记结果页保存前（在 `pet_diary_result_page.dart`）

#### 4.5 实施要求

- 用户输入文本先审查（`diary_input`），不通过直接阻断。
- AI 生成完成后审查输出（`diary_output`），不通过则禁止发布到 `pet_diaries`。
- 公开/私密策略：
  - 若已有公开发布入口，公开必须过服务端审查。
  - 私密可配置为仅本地保存（按产品策略开关）。

### 4.6 AI 生图实验室（`image_input` / `image_output`）

#### 4.6 接入点

- `preparation_page.dart` 上传前与任务启动前
- `loading_page.dart` 任务完成后展示前

#### 4.6 实施要求

- 上传原图后先触发图像审查（`image_input`），通过后才允许 `img-gen-start`。
- 生成完成后对结果图二次审查（`image_output`）：
  - 通过：进入展示/保存
  - 不通过：结果图不落正式桶，提示“生成结果不合规，请更换素材重试”

## 6. 测试与验收标准（前端）

### 6.1 功能用例

- 正常昵称可保存；违规昵称被阻断。
- 违规头像上传被阻断，且本地/临时文件不残留。
- AI 助手违规输入无法发送；违规输出会被替换为安全提示。
- 日记违规输入无法生成；违规输出无法发布。
- 生图违规原图无法启动任务；违规结果图不展示。

### 6.2 性能目标（沿用方案约束）

- 昵称审核交互小于 300ms（理想网络）
- 头像审核交互小于 500ms
- AI 文本审核小于 1000ms
- 生图审核链路小于 3000ms（不含模型生成时间）

### 6.3 DoD（前端完成定义）

- 所有目标页面均接入统一 `ModerationClient`，无绕过写入点。
- 风险提示统一、可本地化、可追踪 `traceId`。
- 新增代码通过 `flutter analyze`，且核心流程具备 widget/service 级测试。

---

## 7. 与后端协作要求

- 需要后端提供并稳定以下 Edge Functions：`moderate-text`、`moderate-image`。
- 需要后端提供统一错误码与 `traceId`，前端按错误码映射文案。
- 需要后端明确 `scene` 枚举并冻结版本，避免联调阶段频繁变更。

---

## 8. 常见失败场景与前端兜底

- 审查服务超时：提示“审核超时，请稍后重试”，禁止高风险场景放行。
- 网络断开：保留输入内容，允许用户一键重试。
- 后端结构变更：通过 `ModerationResult.safeParse` 做兼容，避免页面崩溃。
