# 敏感内容审查前后端联调与上线指导文档（联合实施）

## 1. 文档目标

把前端与后端的敏感内容审查改造收敛为一套可执行的联调、验收、上线流程，确保：

- 所有目标场景联通并可验证
- 关键指标达标（拦截正确率、响应时延、稳定性）
- 上线可灰度、可回滚、可追踪

---

## 2. 联调范围（必须全覆盖）

- 用户昵称、宠物昵称、主人称呼
- 用户头像、宠物头像
- AI 助手输入、AI 助手输出
- 成长日记输入、成长日记输出
- AI 生图原图输入、生成图输出

---

## 3. 前后端统一契约（冻结版）

## 3.1 场景枚举

- `nickname`
- `owner_nickname`
- `pet_name`
- `avatar`
- `pet_avatar`
- `ai_input`
- `ai_output`
- `diary_input`
- `diary_output`
- `image_input`
- `image_output`

## 3.2 审查响应结构

```json
{
  "passed": true,
  "scene": "diary_input",
  "riskLevel": "none",
  "riskLabels": [],
  "action": "allow",
  "message": "ok",
  "traceId": "uuid"
}
```

## 3.3 错误码约定

- `MODERATION_BLOCKED`：命中违规
- `MODERATION_TIMEOUT`：审查超时
- `MODERATION_PROVIDER_ERROR`：第三方异常
- `MODERATION_UNAUTHORIZED`：鉴权失败
- `MODERATION_INVALID_REQUEST`：参数错误

前端只依赖错误码，不依赖第三方厂商原始字段。

---

## 4. 联调准备清单

## 4.1 后端准备

- `moderate-text`、`moderate-image` 部署到测试环境
- `moderation_logs`、`moderation_errors` 表已创建并可写
- 存储桶与 RLS 已配置（临时桶不可公开）
- 提供测试账号和 Postman/curl 样例

## 4.2 前端准备

- 所有目标入口已接入统一 `ModerationClient`
- UI 已支持“通过/拦截/异常”三态提示
- 关键流程支持重试，且不会重复提交脏数据

## 4.3 数据准备

- 文本违规样例（涉政/暴恐/色情等）
- 图像违规样例（血腥、色情、恐怖元素）
- 正常样例（避免误杀）

---

## 5. 联调执行计划（按阶段）

结合“实施参考建议”落地为 3 段联调节奏：

## 阶段 A：接口契约联调（T+0 ~ T+1）

- 先打通 `nickname` 与 `avatar` 两条最小闭环
- 校验响应字段、错误码、`traceId` 贯通
- 通过标准：前端可准确区分通过/拦截/异常

## 阶段 B：核心业务联调（T+1 ~ T+3）

- AI 助手：输入与输出双审查
- 日记：输入与输出双审查
- 生图：原图审查与结果图审查

通过标准：

- 不存在“未审先写/先展示后撤回”的漏口
- 关键链路无 5xx 高频错误

## 阶段 C：全链路回归与压测（T+3 ~ T+4）

- 全场景回归 + 异常注入（超时、鉴权失败、第三方失败）
- 验证日志落库完整性与查询可用性

---

## 6. 联调用例矩阵（最小必测）

## 6.1 文本类

- 正常昵称 -> 通过并写库
- 违规昵称 -> 阻断，数据库值不变
- AI 输入违规 -> 不发请求到聊天模型
- AI 输出违规 -> 显示安全替代文本
- 日记输出违规 -> 禁止发布

## 6.2 图像类

- 正常头像 -> 临时桶 -> 过审 -> 正式桶
- 违规头像 -> 临时桶删除或过期清理，不入正式桶
- 生图原图违规 -> 任务不启动
- 生图结果违规 -> 不落正式桶，不展示

## 6.3 安全类

- 篡改他人 `storage_path` -> 返回越权错误
- 无 token 调用 -> 401
- 伪造 token -> 401

## 7. 观测与指标

## 7.1 必收指标

- `moderation.request.count`
- `moderation.block.count`
- `moderation.error.count`
- `moderation.latency.p95`
- `moderation.false_positive.feedback.count`（前端反馈）

## 7.2 日志追踪

- 所有前端拦截提示都带 `traceId`（可复制到客服/排查）。
- `traceId` 在 `moderation_logs` 与 `moderation_errors` 可关联。

---

## 8. 上线策略

## 8.1 灰度

- 第 1 批：仅昵称+头像场景
- 第 2 批：AI 助手与日记
- 第 3 批：生图链路

每批观察至少 24 小时后再扩大。

## 8.2 回滚

- 前端：开关位关闭审查拦截 UI（但后端触发器保留）
- 后端：函数回滚到上一版本；触发器可临时降级为日志模式
- 数据层：日志表保留，不回滚

## 8.3 上线门禁（全部满足才可放量）

- 全量 P0/P1 缺陷为 0
- 关键链路成功率 >= 99%
- 文本审查 P95 <= 1000ms
- 图像审查 P95 <= 3000ms（不含上游生图耗时）

## 10. 常见联调问题与处理建议

- 前端提示“审核超时”但后端无日志：优先查网关/CORS/鉴权中间层。
- 后端判定通过但前端阻断：检查错误码映射是否被旧逻辑覆盖。
- 生图任务已启动但最终被拦截：确认结果图是否写入了错误桶，避免数据泄漏。
- 高频误杀：先调阈值与 `scene` 策略，再考虑增加人工复核白名单。
